# Phase 0 Session Log

この文書は、Phase 0の計画、判断及び作業の引継ぎを一か所にまとめる
軽量なSession Logである。個人開発で無理なく更新できるように、
コマンド履歴や細かな作業時刻ではなく、目的、結果、判断及び次の作業を残す。

同じ構成を将来の`phase_n.md`へコピーして利用できる。

## 1. Phase概要

| 項目 | 内容 |
|---|---|
| Phase | 0: Goal分解と資産査定 |
| 予定期間 | 2026年8月 |
| 状態 | 準備中 |
| 目的 | GoalとMVP受入条件を実装可能な作業へ分解し、現在の材料の再利用方針を決める |
| 完了ゲート | 候補レビューの一連の流れと、Phase 1で作るデータ契約の対象を説明できる |

## 2. Session開始時に読む文書

毎回すべての資料を読み直す必要はない。次の順に確認し、
変更がない文書は見出しと関連箇所だけを読む。

| 順番 | 文書 | 確認する内容 |
|---|---|---|
| 1 | [SCOPE.md](../../SCOPE.md) | Goal、MVP範囲、原則、受入条件、変更管理 |
| 2 | [AGENTS.md](../../AGENTS.md) | 実装・データ・検証で守る作業原則 |
| 3 | [DRR_long_term_plan.md](../DRR_long_term_plan.md) | 現在のPhase、前後の依存関係、判断ゲート |
| 4 | このSession Log | 前回の結果、未決事項、今回の開始パック |
| 5 | [README.md](../../README.md) | システム全体像を再確認したい場合 |

作業対象のコードやデータは、今回の目的に関係するものだけ追加で読む。
現在のリポジトリ全体を、毎回最初から調査し直さない。

## 3. Session開始パック

Session開始時に、次を短く埋める。1項目1〜2行でよい。

```markdown
### YYYY-MM-DD Session N

- 今日の目的:
- 関連するGoal・受入条件:
- 前回からの引継ぎ:
- 使用する文書・データ:
- 今日決めること:
- 終了条件:
```

重要なドメイン判断が不足している場合は、推測して実装せず、
未決事項として残して確認する。

## 4. Phase 0の対象

### 実施すること

- GoalとMVP受入条件を、検証可能な確認項目へ変換する。
- 区域内、区域外、部分重複及び情報不足を含む代表候補を10〜20件選ぶ。
- 候補1件分の理想的な情報構造を作る。
- 現在の材料を「再利用」「アダプター化」「凍結」「不明」に分類する。
- 最初の縦切りを「候補1件の取込、表示、レビュー及び履歴保存」として定義する。
- Phase 1で確定するデータ契約の範囲と未決事項を整理する。

### 実施しないこと

- 候補生成パイプラインの本格的な書き直し
- 技術者レビュー画面の本実装
- 土砂災害以外の災害モデルの開発
- 全国展開又はリアルタイム処理
- 特定クラウドを前提とした本番構成の決定

## 6. 予定Session

| Session | 主題 | 主な完了条件 |
|---|---|---|
| 0 | Phase準備 | Goal、ローカルファースト方針、長期計画及びログ形式が揃う |
| 1 | Goalと受入条件の分解 | 各受入条件に確認方法と必要な情報を対応付ける |
| 2 | 代表候補と理想データ | 代表候補を選び、候補1件の必要情報を具体化する |
| 3 | 現在の材料の査定 | 再利用、アダプター化、凍結、不明を理由付きで分類する |
| 4 | 縦切り設計とPhase判定 | Phase 1の入力、出力、未決事項及び最小実装を確定する |

Session数は目安とし、成果物が小さければ統合し、判断待ちの場合は分割する。

## 7. 判断ログ

設計や範囲に影響する判断だけを残す。単純なファイル編集は記録しない。

| ID | 日付 | 判断 | 理由・影響 |
|---|---|---|---|
| D-0001 | 2026-07-26 | 最初のMVPはローカル環境だけでも中核フローを実行可能にする | 外部サービスの利用期限や費用にGoalを拘束させない |
| D-0002 | 2026-07-26 | Earth Engine等の外部サービスは任意のアダプターとして扱う | 利用可能な機能は活用しつつ、唯一の実行・保管手段にしない |
| D-0003 | 2026-07-26 | 現在のコード、データ及びPoC成果は検証後に再利用する材料とする | 既存構成から要件を逆算せず、必要ならスクラッチから再設計する |

## 8. 作業ログのフォーマット

各Sessionの終了時に、開始パックの下へ次を追記する。

```markdown
#### 実施内容

- 何を確認・変更したか

#### 結果・判断

- 分かったこと、決めたこと

#### 確認

- テスト、目視確認、未実施の確認

#### 未決事項

- 次へ持ち越す判断や不足情報

#### 次のSession

- 最初に行う具体的な1〜3項目
```

問題がなければ「未決事項: なし」と記載する。詳細な調査結果や長い表が
必要になった場合は別文書へ分け、このログからリンクする。

## 11. Session終了時の確認

- Phase成果物のチェック状態を更新した。
- 新しい設計判断を判断ログへ追加した。
- 実施した確認と未実施の確認を区別した。
- 未決事項を残した。
- 次回Sessionの最初の作業を1〜3項目に絞った。
- Goal又はMVP範囲を暗黙に変更していない。
