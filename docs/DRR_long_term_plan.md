# DRRシステム 長期作業計画

## 1. 目的

本書は、`SCOPE.md`のGoalに向けて、週末を中心に進める設計、実装、
検証及び運用準備を、1〜2か月単位の作業に分割した計画である。

現在利用できるコード、データ、SQL、GIS成果及び外部サービスは、
Goal実現に使える可能性がある材料として評価する。既存構成の維持や
特定技術の継続利用を目的とせず、Goalと受入条件に適合するものだけを
検証した上で再利用する。

## 2. 計画の前提

- 開始時期: 2026年8月
- 作業体制: 1人を基本とし、必要に応じて防災技術者のレビューを受ける
- 作業時間: 週末6〜10時間、月24〜40時間程度
- 最初のMVP: 宮崎県延岡市及びその周辺の土砂災害
- 仮説の空間単位: 候補ポリゴン
- MVP評価時期の目安: 2027年6月
- 実運用試行の目安: 2027年8月
- 長期Goalに向けた基盤評価の目安: 2027年10月

日程は実装量だけでなく、データの利用条件確認、防災技術者のレビュー、
現地知見との照合に左右される。期間を守るために受入条件を省略しない。

## 3. 技術方針

### 3.1 ローカルファースト

最初のMVPの中核フローは、外部クラウドサービスを利用しなくても、
ローカル環境と公開形式のデータで実行できるようにする。

```text
公式・公開データ
    ↓
取得・検証アダプター
    ↓
ローカルデータ（GeoTIFF、GeoPackage、GeoJSON、GeoParquet等）
    ↓
再現可能な分析Run
    ↓
候補仮説＋支持根拠＋反証＋不確実性＋情報不足
    ↓
地図表示・技術者レビュー
    ↓
現地調査・事後検証・手法改善
```

重要な入力、出力及び来歴を外部サービスだけに置かない。大容量データは
Gitへ直接格納せず、取得方法、提供元、版、ライセンス、チェックサム及び
小規模な検証用データをリポジトリで管理する。

### 3.2 Earth Engineの位置付け

Earth Engineは、利用可能な期間に次の目的で使用できる任意アダプターとする。

- 広域データの探索及び可視化
- 衛星画像の一時的な前処理
- ローカル処理結果との比較
- 初期データ又は検証用成果の出力

Earth Engine Assets及びGoogle Driveは一時的な入出力先として使用できるが、
システムの正本や唯一の再現手段としない。BigQuery、Cloud Storage、
Cloud Runその他の有償Google Cloudサービスは、MVPの必須構成に含めない。

### 3.3 目標アーキテクチャ

中核では少なくとも次の概念を扱う。

- `CandidateHypothesis`
- `Evidence`及び`CounterEvidence`
- `Uncertainty`及び`MissingInformation`
- `Source`及び`MethodRun`
- `ReviewDecision`
- `VerificationResult`

GIS、データベース、外部API、Earth Engine及び画面は中核から分離し、
アダプターを介して接続する。

## 4. 現在の材料の扱い

### 4.1 再利用候補

- DEM、傾斜、流向及びラスタ・ベクタ変換の処理
- 土砂災害候補ポリゴンとその属性例
- 既存警戒区域及び地質情報との空間照合
- 地図及び属性情報の診断用表示
- Earth Engineによる探索的な候補抽出
- BigQuery GISで検証した空間演算及びテーブル構造

再利用前に、CRS、NoData、閾値、入力版、ライセンス、処理履歴及び
再現性を確認する。既存出力から元処理を推測して原手法とはみなさない。

### 4.2 アダプター化するもの

- Earth Engine
- QGIS
- BigQuery等の外部データベース
- 外部ストレージ及び外部API

これらは利用可能な場合の補助機能とし、中核のドメインモデル、
レビュー判断及び保存形式を拘束させない。

### 4.3 最初のMVPでは凍結するもの

- 土砂災害以外の災害モデル
- 石油・資源探査を対象としたGeoSemantic実験
- LLMによるクラスタ解釈
- 全国規模及びリアルタイムの処理
- 技術選定を先行して作成された概念実装

削除の判断は急がず、MVP受入条件への寄与が確認できるまで参照材料として隔離する。

|---|---|---|---|
| 0. Goal分解と資産査定 | 2026年8月 | Goalと受入条件の対応付け、代表候補の選定、既存材料の再利用判定、技術上の判断記録 | 受入条件対応表、代表候補10〜20件、再利用・隔離一覧。候補レビューの一連の流れを説明できれば完了 |

| 6. 実運用試行 | 2027年7〜8月 | 認証、バックアップ、更新手順、障害時運用、データライセンス、監視及び住民への還元手順 | 外部サービス停止時を含む運用手順。限定利用者による継続運用が可能なら試行完了 |
| 7. 相互運用と次段階 | 2027年9〜10月 | 標準形式での入出力、API、公式情報更新との接続、別地域又は別データ源での移植確認 | 技術固有依存を増やさず移植できれば、地域拡張・マルチハザード化の次期計画へ進む |

## 6. 各月の週末サイクル

各1か月の作業は、原則として次のサイクルで進める。

1. 第1週: 目的、受入条件、未確定事項及び代表データを確認する。
2. 第2週: 最小単位を実装し、単体テストを追加する。
3. 第3週: 地理空間検証、来歴確認及び失敗例のテストを行う。
4. 第4週: 成果をデモし、判断記録、文書及び次月計画を更新する。

2か月フェーズでは、1か月目に縦切りの最小実装、2か月目に例外処理、
検証、利用者確認及び判断ゲートを実施する。

## 7. 最初の週末に行うこと

1. `SCOPE.md`の各受入条件を、実行可能な確認項目へ変換する。
2. 既存候補から、区域内、区域外、部分重複及び情報不足を含む代表例を選ぶ。
3. 候補1件分の理想的なデータ例を作り、必須ドメイン情報を確認する。
4. 現在の材料を「再利用」「アダプター化」「凍結」「不明」に分類する。
5. 最初の縦切りを「候補1件の取込、表示、レビュー及び履歴保存」に固定する。

## 8. 判断ゲート

- Gate 1: データ契約がGoalとMVP受入条件を表現できる。
- Gate 2: 外部サービスなしで候補を再生成できる。
- Gate 3: 候補ごとの根拠、反証、不確実性及び情報不足を説明できる。
- Gate 4: 技術者がレビューを完遂し、判断履歴を追跡できる。
- Gate 5: 代表候補によって追加調査判断への有用性を評価できる。
- Gate 6: 外部サービス停止時にも保存済み情報を参照し、限定運用を継続できる。

ゲートを満たさない場合、次フェーズの機能追加より、原因の特定、
設計修正又は対象範囲の再確認を優先する。

## 9. 主なリスクと対応

| リスク | 対応 |
|---|---|
| 防災技術者のレビュー機会を確保できない | フェーズ4までに候補と評価票を準備し、レビュー可能な時間を早期に調整する |
| 公式データの版やライセンスが不明 | データ目録で取得元、版、取得日、利用条件及びチェックサムを必須化する |
| Earth Engineが利用できなくなる | ローカル処理を基準実装とし、必要な成果を公開形式で退避する |
| ローカル計算が長時間化する | 対象範囲、解像度及び処理単位を制限し、キャッシュと段階処理を導入する |
| 既存処理の再現条件が不足する | 再現性を`partial`又は`unavailable`として記録し、原手法として移植しない |
| 候補を危険区域又は発生確率と誤解される | 表示、用語、レビュー手順及び説明文で`screening_candidate`を一貫して示す |

## 10. 計画の更新

各フェーズ終了時に、進捗、受入条件、未検証事項、残存リスク及び
次フェーズへの影響を更新する。

Goalの変更は本計画では行わない。Goal又はMVP範囲の変更が必要な場合は、
`SCOPE.md`のChange Controlに従い、ユーザーの明示的な承認を得る。
